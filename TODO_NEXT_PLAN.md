# План редизайна Coins Kids Shop (весь сайт + кабинет + админка)

## Краткое summary

Цель редизайна: сделать интерфейс понятным детям 6–14 лет, эффективным для родителей и управляемым для админки, без смены текущего стека (server-rendered HTML + vanilla JS + CSS partials).
Подход: эволюционный редизайн по слоям (UX-потоки → IA → design system → экраны → motion/gamification → mobile/perf) с отдельными UX-сценариями для ролей child, parent/admin, super_admin.

———

## 1) UX-аудит (типовые и ожидаемые проблемы)

### Текущие сильные стороны (на базе репо)

1. Уже есть разделение ролей и секций (tasks, shop, requests, history, settings, analytics).
2. Есть mobile-паттерны: bottom-nav, safe-area, bottom-sheet модалки.
3. Есть базовые элементы геймификации: монеты, лимиты, прогресс, бейджи/иконки в UI.

### Возможные проблемы текущего UX

1. Навигация перегружена для детей: слишком много разделов первого уровня + “More” меню.
2. Информационная плотность высока: карточки и статистика конкурируют за внимание.
3. Недостаточная иерархия “что делать сейчас”: нет явного next-best-action для ребенка.
4. Смешение “операционных” и “эмоциональных” состояний: достижения и управление лимитами визуально равнозначны.
5. Родительские действия (подтверждения/лимиты/редактирование) не выделены как отдельный режим “управления”.
6. Админка и родительский UX визуально близки, хотя задачи сильно отличаются.
7. Есть риск визуальной “взрослости” на некоторых экранах для младшей группы 6–9 лет.

### UX-риски для детей 6–14

1. Мелкие tap targets в навигации и карточках для маленьких экранов.
2. Переизбыток текста в карточках задач/наград и в модалках.
3. Неочевидные статусы заявки (pending/approved/rejected) без яркой state-модели.
4. Слабая reward-feedback петля: после действия не всегда достаточно “ощутимый” отклик.
5. Когнитивная перегрузка из-за множества вторичных разделов (rules/about/friends/settings).

### Точки фрустрации

1. Ребенок: “что можно купить сейчас?” не всегда видно сразу.
2. Родитель: подтверждение заявок и контроль лимитов разнесены по разным секциям.
3. Родитель: редактирование задач/наград требует лишних переходов.
4. Ребенок: ожидание решения по заявке без ясного ETA и статуса.
5. Все роли: длинные модалки на мобильном при вводе нескольких полей.

### Проблемы адаптивности и mobile

1. Bottom-nav может становиться тесной при росте количества пунктов.
2. В mobile “More” dropdown добавляет лишний уровень навигации.
3. Карточки с длинными названиями теряют читаемость.
4. Стат-блоки и аналитика визуально тяжелы на телефоне.
5. Возможны layout-shift из-за динамического контента и загрузки графиков.

## 2) Новая информационная архитектура

## Ролевая модель (обязательная)

1. Child App — выполнение задач, покупка наград, отслеживание прогресса.
2. Parent App — подтверждение заявок, настройка задач/наград/лимитов.
3. Admin Panel (super_admin) — системное управление семьями, базой, каталогами.

## Структура Child App

1. Главная (Today): баланс, “сделай сейчас”, быстрый прогресс дня.
2. Задания: список + фильтры “быстрые/дом/учеба”.
3. Награды: карточки магазина, доступные сейчас, wishlist.
4. Прогресс: уровни, бейджи, streak, история достижений.
5. Профиль: ник, друзья, настройки.

## Структура Parent App

1. Обзор: сводка по детям, pending-заявки, лимиты.
2. Заявки: входящие, массовые действия approve/reject.
3. Контент: задачи, награды, категории, шаблоны.
4. Лимиты: дневные/месячные правила, частотность, крупные покупки.
5. Семья: ссылки входа, профили детей, безопасность.

## Структура Super Admin

1. Семьи: список, фильтры, карточка семьи.
2. Каталоги: базовые задания/награды.
3. Система: бэкап/восстановление/диагностика.
4. Аудит: ключевые события/ошибки (read-only).

## Мобильные отличия IA

1. Child mobile: 4 bottom-tab (Главная, Задания, Награды, Прогресс), Профиль в avatar menu.
2. Parent mobile: 4 bottom-tab (Обзор, Заявки, Контент, Лимиты), Семья в More.
3. Desktop/tablet: боковая навигация для parent/admin, top+tabs для child.

## 4) UI-концепция

## Визуальный стиль

1. Playful Minimal: чистая композиция + яркие reward-акценты.
2. Child UI: крупные формы, меньше текста, эмоциональные статусы.
3. Parent/Admin UI: выше плотность, спокойная палитра, четкая иерархия действий.

## Цветовая палитра (пример)

1. Base: #0F172A (фон), #111827 (surface), #E5E7EB (text).
2. Primary child-action: #22C55E.
3. Coins/reward accent: #F59E0B.
4. Parent control accent: #3B82F6.
5. Danger/limit: #EF4444.
6. Neutral states: #94A3B8.

## Типографика

1. Headline: Manrope (или Nunito Sans) 700/800.
2. UI text: Inter/Nunito Sans 500/600.
3. Min sizes: mobile 16px body, 14px secondary, 20–24px key numbers.

## Кнопки и карточки

1. Primary CTA: высокая контрастность, крупный hit-area, один главный CTA на экран.
2. Reward card: цена, доступность, лимит, бейдж редкости, одно основное действие.
3. Task card: expected effort, монеты, частота, статус выполнения.

## Анимации и микровзаимодействия

1. Мягкий feedback на earn/spend (120–220ms).
2. Reward claim animation: coin burst + success state.
3. Pending state pulse для заявок.
4. prefers-reduced-motion обязателен.

## Принципы адаптивного UI

1. Mobile: single-column, sticky action bar, bottom-sheet forms.
2. Tablet: 2-column cards + split panels.
3. Desktop: 3-column content + persistent navigation rail.
4. Компоненты перестраиваются по container queries, не только viewport breakpoints.

## 5) Геймификация

1. Прогресс-бары: день, неделя, до награды.
2. Уровни: XP от задач, видимый следующий milestone.
3. Бейджи: “7 дней подряд”, “помощник дома”, “бережливый покупатель”.
4. Ачивки с коллекцией и rarity (common/rare/epic) без pay-to-win логики.
5. Событие получения награды: анимация + карточка “что открылось дальше”.
6. Мобильные паттерны:

- Sticky progress chip вверху.
- Pull-to-refresh как “обновить прогресс”.
- Haptic-like feedback через визуальный импульс (web-safe).

## 6) Мобильная стратегия (обязательно)

## Подход

1. Mobile-first для Child App.
2. Adaptive-first для Parent/Admin (mobile поддерживается, desktop оптимизируется под плотность).

## Навигация mobile

1. Bottom navigation до 4 основных пунктов.
2. Secondary действия в sheet/menu, не в основном таб-баре.
3. Back-stack логика: всегда понятно, где пользователь и как вернуться.

## Размеры интерактивных элементов

1. Tap targets: минимум 44x44px, для child-critical CTA 48–52px.
2. Межэлементный отступ: не меньше 8px.
3. Важные CTA закреплять в нижней зоне большого пальца.

## Упрощение интерфейса

1. Один главный вопрос на экран: “что сделать сейчас?”
2. Убрать вторичные метрики из child-экранов в скрытые детали.
3. Формы разбить на шаги 1–2–3 вместо длинных модалок.

## Поведение карточек наград

1. Mobile: вертикальная карточка с priority-полями (название, цена, статус).
2. Быстрые состояния: доступно, коплю, нужен запрос.
3. Sticky фильтры: категория, доступность, цена.

## Bottom nav / tabs / жесты

1. Bottom nav фиксирован, safe-area-aware.
2. Horizontal swipe между child primary tabs (опционально, с отключением в accessibility).
3. Pull-to-refresh только на списках.

## Оптимизация скорости

1. Lazy render тяжелых секций (analytics/charts).
2. Отложенная загрузка вторичных JS модулей.
3. Минимизация layout shift: фиксированные skeleton размеры.
4. Цель mobile web vitals: LCP < 2.5s, INP < 200ms, CLS < 0.1.

## 7) План внедрения (этапы)

## Этап 1 — Быстрые UX-улучшения (1–2 спринта)

1. Упрощение child mobile nav.
2. Единые состояния заявок.
3. Укрупнение tap targets.
4. Улучшенные empty/loading/error states.
5. Базовые метрики UX (воронка задач/покупок/заявок).

## Этап 2 — Переработка структуры (2 спринта)

1. Новая IA по ролям.
2. Экран “Сегодня” для ребенка.
3. Parent Inbox-first.
4. Реструктуризация разделов settings/limits/content.

## Этап 3 — Визуальный редизайн (2 спринта)

1. Design system v2 (tokens + component library).
2. Обновление карточек, кнопок, форм, типографики.
3. Редизайн landing/login/public pages.
4. Редизайн super_admin панелей.

## Этап 4 — Геймификация и motion (1–2 спринта)

1. Уровни, бейджи, коллекция ачивок.
2. Reward animations и feedback states.
3. Прогресс-петли “день/неделя/до цели”.

## Этап 5 — Мобильная оптимизация и hardening (1 спринт)

1. Performance pass (lazy-load, code split, skeletons).
2. Accessibility pass (контраст, focus, reduced motion).
3. Device QA: смартфоны/планшеты/desktop.
4. Подготовка rollout + feature flags + post-release мониторинг.

## Изменения интерфейсов/API/типов (важно для команды)

1. UI state модель:

- userRole: child | parent | super_admin
- requestStatus: pending | approved | rejected | expired
- rewardAvailability: available | insufficient_coins | limit_reached | parent_approval_required

2. Новые/обновленные client events:

- task_completed, reward_requested, reward_claimed, request_decided, streak_updated.

3. Данные для геймификации:

- xp, level, streakDays, badges[], nextMilestone.

4. Компонентные контракты:

- Card props: title, meta, status, primaryAction, secondaryActions, badge.

5. Навигационный контракт:

- Child primary tabs строго фиксированы (max 4), secondary через menu/sheet.

## Тест-кейсы и acceptance criteria

1. Child mobile: за 1 сессию находит задачу, отправляет запрос/выполняет действие, видит обновленный прогресс.
2. Parent mobile: обрабатывает входящую заявку за ≤3 шага.
3. Parent desktop: создаёт награду с лимитом без перехода по >1 дополнительному экрану.
4. Статусы заявок читаются без дополнительного текста (цвет + иконка + label).
5. Карточки корректно отображаются на 320px, 768px, 1024px+.
6. Модалки/шейты не ломают ввод на iOS/Android клавиатуре.
7. prefers-reduced-motion отключает необязательные анимации.
8. Web vitals соответствуют целям на мобильном.
9. UI regression: ключевые сценарии tasks/shop/requests/history/settings/super-admin проходят.
10. Геймификация не мешает основному сценарию (нет блокирующих анимаций >300ms).

———

## Явные assumptions и выбранные defaults

1. Скоуп принят: весь сайт, включая кабинет и админку (super_admin).
2. Технологический стек сохраняется: vanilla JS + server-rendered HTML + текущая модульная структура.
3. Редизайн выполняется итерационно без “big-bang” релиза.
4. Основной фокус первой волны: child mobile UX и parent request flow.
5. Геймификация вводится постепенно и не меняет базовую бизнес-логику начисления/списания монет.
