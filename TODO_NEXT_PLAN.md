## План E2E-покрытия магазина и лендинга (уровень: Максимальный)

### Краткое резюме

Цель: довести покрытие tests/ui-e2e от текущих 2 файлов (auth/layout) до полного регресса по лендингу и рабочим потокам магазина (admin + child), включая лимиты, статусы заявок, историю и негативные кейсы.
Подход: фазовая доставка с приоритетами P0/P1/P2, где каждая фаза автономна и может выполняться отдельным агентом.

### Изменения в интерфейсах/контрактах

- Публичные продуктовые API не меняем (/api/data, /api/base-data, /features/*, / остаются без изменений).
- Добавляем только тестовые интерфейсы:

1. tests/ui-e2e/helpers/appHarness.js — запуск приложения, загрузка фикстур, хелперы cookies/role.
2. tests/ui-e2e/helpers/networkMocks.js — централизованные моки GET/POST /api/data, GET /api/base-data.
3. tests/ui-e2e/fixtures/*.json — наборы данных состояний (admin, child, лимиты, пустой магазин, ошибки API).
4. Теги/группы тестов в именах @landing, @shop-admin, @shop-child, @limits, @regression.

### Фаза 1. Базовый тестовый контур и стабильность (P0)

- Задача: стандартизировать запуск E2E с единым harness, чтобы последующие фазы были детерминированны.
- Шаги:

1. Вынести повторяющиеся действия Playwright в helper-слой (gotoAppAsAdmin, gotoAppAsChild, openTab, waitForDataReady).
2. Ввести фикстуры состояния для shop/request/history и отдельный набор для ошибок API.
3. Добавить сетевые моки и явные ожидания запросов GET /api/data, POST /api/data.
4. Зафиксировать правила стабильности: таймауты, ожидание рендера, запрет на sleep без причины.

- Результат фазы: новый каркас тестов, который переиспользуется во всех остальных фазах.

### Фаза 2. Лендинг и публичные страницы (P0)

- Задача: закрыть весь работающий public-flow для /, /features/tasks, /features/shop, /about, /faq, /blog entry-point.
- Шаги:

1. Проверить, что неавторизованный / показывает landing.html.
2. Проверить верхнюю навигацию (public-top-nav) и переходы по ключевым ссылкам.
3. Проверить CTA-кнопки лендинга и feature-страниц (/login.html, /features/*).
4. Проверить базовую адаптивность на desktop/mobile (критические блоки видимы, нет поломки навигации).
5. Проверить 404/невалидные feature slug через /features/<invalid>.

- Результат фазы: полный регресс публичного контура и маршрутизации лендинга.

### Фаза 3. Магазин: поток админа (P0)

- Задача: покрыть полный CRUD и отображение shop-карточек для admin.
- Шаги:

1. Переход на вкладку shop, проверка empty-state.
2. Добавление товара через shop-modal с проверкой полей name/price/group/type/frequency/money_limit.
3. Проверка появления карточки, бейджей, статуса доступности, кнопок действий.
4. Редактирование товара и валидации (пустое имя, некорректная цена).
5. Удаление товара и проверка isDeleted-поведения в UI.
6. Проверка фильтрации товаров по currentChildId для admin.

- Результат фазы: подтверждённая рабочая ветка управления магазином родителем.

### Фаза 4. Магазин: поток ребенка и жизненный цикл заявки (P0)

- Задача: покрыть child-покупку и полный lifecycle shop_purchase.
- Шаги:

1. Child: отправка заявки на покупку, проверка записи в requests со статусом pending.
2. Admin: открытие входящих, approve заявки, проверка списания баланса и записи в history (spend, itemId, moneyAmount).
3. Admin: reject заявки, проверка статуса rejected, отсутствия списания.
4. Child: отображение собственных заявок (my-requests) и смены статусов.
5. Проверка счетчика заявок в nav и summary-блока статусов.

- Результат фазы: покрыт основной бизнес-процесс магазина между ролями.

### Фаза 5. Лимиты, ограничения и edge-cases (P1)

- Задача: покрыть текущую рабочую логику ограничений и крайние сценарии.
- Шаги:

1. Недостаточно монет: покупка блокируется, корректный текст ошибки.
2. monthlyLimit: превышение месячного лимита и корректный отказ.
3. large покупка: запрет второй крупной покупки в месяц.
4. frequency.limit/period: запрет при исчерпанной частоте.
5. Проверка moneyAmount-меток в request/history.
6. Негативные API-кейсы POST /api/data (403/5xx): UI не падает, ошибка видна.

- Результат фазы: бизнес-ограничения магазина проверены end-to-end.

### Фаза 6. Полный регресс, матрица окружений и CI-гейтинг (P1/P2)

- Задача: сделать покрытие регулярным и пригодным для релизного контроля.
- Шаги:

1. Разделить suite на smoke/regression по тегам и времени прогона.
2. Включить прогон в обязательную последовательность проверки: npm run lint, npm test, npm run build, npm run test:ui:e2e.
3. Добавить отчётность по сценариям и список flaky-тестов с планом стабилизации.
4. Зафиксировать manual-checklist для критических shop-flow (add/edit/delete, direct purchase, child request + admin decision, limits).

- Результат фазы: воспроизводимый релизный E2E-процесс с понятными quality gates.

### Набор тест-кейсов (обязательный минимум для “Максимальный”)

1. Лендинг: загрузка и CTA-навигация.
2. Публичные страницы: feature/tasks/shop/about/faq/blog.
3. Shop admin CRUD: add/edit/delete + empty-state + child filter.
4. Shop child request flow: pending → approved/rejected.
5. Баланс и history: корректные изменения после approve purchase.
6. Лимиты: coins, monthly, large-per-month, frequency.
7. Ошибки API сохранения: корректный fallback UI.
8. Mobile viewport: критические сценарии лендинга и shop.
9. Десктоп viewport: полный регресс магазина.
10. Невалидные публичные маршруты/slug.

### Критерии приёмки

- Все P0 фазы зелёные и стабильные при 3 последовательных прогонах.
- Нет flaky в критических сценариях магазина и лендинга.
- Покрыты обе роли (admin, child) и все переходы статусов pending/approved/rejected.
- Проверки выполняются в стандартном пайплайне проекта, включая npm run test:ui:e2e.

### Явные допущения и выбранные дефолты

- Выбран режим покрытия: Максимальный.
- E2E строится без изменения продуктовой логики, через тестовый harness + фикстуры + сетевые моки.
- Первым приоритетом считаем стабильность и детерминированность, затем расширение матрицы кейсов.
- Основной фокус: текущий работающий функционал магазина и лендинга, без расширения на новые фичи.
